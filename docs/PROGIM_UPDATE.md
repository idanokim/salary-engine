# איך מעדכנים את ה-Progim כדי שהסימולטור יישאר נכון

מדריך זה מסביר (א) איך לתחזק את חוברת ה-Progim עצמה, ו-(ב) איך להזין אותה
לתוכנה. הוא מבוסס על כל התקלות שנתפסו בפועל בעבודה מול קבצי 2008–2026.

---

## כלל הזהב: לשלוח תמיד את ה-xlsm המקורי

**לא לשמור מחדש כ-xlsx.** שמירה כ-xlsx מוחקת את ערכי-המטמון של חלק מנוסחאות
האחוזים (tosafot שורות 2–3), והחילוץ מאבד כללים — ראינו זאת בפועל: חילוץ
מ-xlsx איבד 6 כללי אחוזים. החוקה נקראת גם מהנוסחאות וגם מהערכים המחושבים,
ולכן שני הצדדים חייבים להיות שלמים.

בנוסף: לא לשנות שמות גיליונות ולא להזיז את בלוק החוקה. התוכנה מזהה לפי:

| גיליון | מה נקרא ממנו |
|---|---|
| `DARGA` | תווית דרגה → שכר יסוד (עמודות B, D) |
| `vetek` | מקדמי ותק לכל מסלול (שורה 1 שם, שורה 2 קוד דירוג) |
| `DERUG` | תקרות ותק ושמות מסלולים |
| `SACHAR` בלוק `AA3:DV11` | **החוקה**: שורה 9 סמל, שורה 10 שם, שורה 7 אחוז, שורה 11 נוסחת הסכום (הרכב הבסיס) |
| `tosafot ` (עם רווח בסוף!) | אחוזים וסכומים שוטפים (שורות 2–3) |
| `Netunei Gimlai` עמודות E–J | טבלת הזכאות; **H='ידני' ⇒ הערך מעמודה J** (רכיב מדווח, לא מאומת) |
| `sminimum` שורות 8+ | אילו סמלים נספרים לשכר מינימום (עמודה C ל-1699, עמודה D ל-5260) |
| `heskem 2016` / `heskem 2023` / `tos kibutzi` / `MANMASH 2010` | מדרגות (פעימות) של הסכמי השכר |
| `GMUL MINHAL`, `BATEI MISHPAT 875`, `4550` | סכומי/אחוזי רכיבים ייעודיים |

## איך לעדכן את החוברת עצמה — שיהיה נכון

1. **הסכם שכר חדש / פעימה חדשה** — להוסיף את האחוז החדש **עם תאריך התחולה**
   בטבלת המדרגות (`tos kibutzi` / `heskem …`), **בלי למחוק את המדרגות
   הישנות**. המנוע מקבל כל אחוז רשמי שהיה אי-פעם בתוקף — כך תלושים
   היסטוריים ממשיכים להיבדק נכון. דריסת אחוז ישן = כל קובץ ישן יסומן שגוי.
2. **סמל שכר חדש** — שלושה מקומות:
   - עמודה חדשה בבלוק `SACHAR!AA3:DV11` עם נוסחת הסכום (הרכב הבסיס נלמד
     ממנה אוטומטית);
   - שורה בטבלת הזכאות ב-`Netunei Gimlai` (אם ידני — לכתוב 'ידני' ב-H);
   - שורה ב-`sminimum` עם דגלי 'כן'/'לא' (נספר לשכר מינימום או לא).
3. **סמל עם כמה מספרים (כינויים)** — לכתוב את שניהם בתא הסמל בדיוק בצורה
   `1037 / 4544`. המנוע מזהה את שניהם.
4. **עדכון טבלת שכר (DARGA/vetek)** — להחליף ערכים בלבד, לא מבנה. תוויות
   דרגה עם פלוס נשמרות בצורת `19+` (פלוס בסוף).
5. **לא להטמיע קבועים בנוסחאות** — למשל הקבוע 257.37 בתוך נוסחת 920: אם
   הסכום ישתנה, החוקה תהיה שגויה בלי שאיש ישים לב. עדיף הפניה לתא.
6. **סכומים שקליים של הסכמים** (5402/5524 וכו') — לעדכן את טבלת
   דרגה×מסלול×פעימה בגיליון ההסכם, שוב בלי למחוק ערכי עבר.

## איך מזינים את החוברת לתוכנה

```bash
# 1. טבלאות שכר (דרגות, ותק, תקרות)
python tools/extract_lookups.py path/to/Progim.xlsm lookups.json

# 2. החוקה (כללי הרכיבים)
python tools/extract_rules.py path/to/Progim.xlsm component_rules.json

# 3. אימות מול קובץ גולמי אמיתי לפני פריסה
python -m pytest tests/ -q
python tools/validate_all.py            # אם קיימים קבצי דוגמה
python tools/unified_report.py path/to/golmi.xlsx --out check.xlsx
```

**איפה נשמרת החוברת:** ה-`.xlsm` המקורי נשמר במאגר תחת
[`data/progim/`](../data/progim/) — זה מקור-האמת שממנו חולצו הנתונים
שהאתר משתמש בהם. בכל עדכון: להחליף שם את הקובץ, לחלץ מחדש, ולוודא
שמספר הכללים לא ירד (ראו בדיקת השפיות למטה) — ואז commit + push.

ואז commit + push — הפריסה מרימה את הנתונים החדשים. אין צורך לגעת בקוד.

**בדיקת שפיות אחרי כל עדכון** (חובה לפני פריסה):
- `component_rules.json` מכיל את אותו מספר כללים או יותר (ירידה = החילוץ
  איבד נתונים — כנראה xlsx במקום xlsm).
- הרצת קובץ חודש אמיתי מחזירה אחוז תקינות דומה לקודם. קפיצה חדה בשגויים
  אחרי עדכון חוברת = כמעט תמיד בעיה בחוברת, לא בשכר.

## מה מוגן אוטומטית גם אם טעיתם

- **כיול עצמי**: כלל שלא מתאמת על ‎97%+‎ מהעובדים בקובץ מושתק אוטומטית —
  טעות בחוברת לא תציף סימוני שווא, היא "תיעלם". לכן ירידת כיסוי שקטה היא
  הסימן לחוברת פגומה — בודקים עם בדיקת השפיות למעלה.
- **אחוזים לא-חוקיים** נדחים בחילוץ (אחוז חייב להיות בין 0 ל-1).
- **ערכים היסטוריים** שחסרים בחוברת מגובים ב-`HISTORICAL_RATES` בתוך
  `tools/extract_rules.py` — אם מחזירים חוברת ישנה, הכללים לא נשברים.

## מגבלה מובנית שכדאי להכיר

ה-Progim הוא מחשבון של עובד בודד לחודש הנוכחי: אין בו היסטוריית פעימות
מלאה ואין שכר-בסיס לפי תקופה. את הפער הזה התוכנה משלימה (מדרגות ההסכמים,
זיהוי יעד המינימום מכל קובץ, וכיול עצמי לכל קובץ) — אבל ככל שמוסיפים
לחוברת תאריכי תחולה מסודרים לצד כל שינוי, האימות ההיסטורי נעשה מדויק יותר.
